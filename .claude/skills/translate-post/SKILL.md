# translate-post

`ko/<slug>.md` → `ja/<slug>.md`. **같은 slug를 쓴다** — 이것이 두 언어를 짝짓는 유일한 근거다.

## 절차

1. **원본 Read.** `src/content/blog/ko/<slug>.md`. slug를 못 받았으면 `ko/`에서 아직 `ja/` 짝이
   없는 글 목록을 보여주고 고르게 한다 (`npm run i18n:status`가 그 목록을 뽑는다).

2. **frontmatter 처리 — 여기가 가장 중요하다.**

   - **번역하는 것: `title`, `description` 둘뿐.**
   - **코드값 그대로 복사: `domain`, `project`, `topics`, `type`.**
     이걸 어기면 같은 분류가 언어별로 갈라져 인덱스가 반쪽씩 나뉜다.
   - `publishedAt`은 원본과 같은 날짜를 쓴다. `updatedAt`이 있으면 그대로 복사한다.
   - `draft`는 원본 값을 따른다.

3. **본문 번역.**

   - **문단 구조·제목 계층·표·코드블록을 원본 그대로 유지한다.** 코드블록 안에서는
     **코드는 번역하지 않고 주석은 번역한다.** 주석은 코드가 아니라 설명이고, 그대로 두면
     일본어 독자에게 그 줄만 읽히지 않는다. 식별자·문자열 리터럴·출력값에는 손대지 않는다.
   - **단, 남의 소스를 인용한 코드블록은 주석까지 원문 그대로 둔다.** 프레임워크 소스를
     그대로 보여주는 것이 인용의 요점이므로, 주석을 번역하면 인용이 아니게 된다.
   - 링크 URL, 이미지 경로는 손대지 않는다.
   - **직역이 아니라 일본어 기술 문서로 읽히게 쓴다.** 한국어 기술 문서의 어투를 그대로 옮기면
     어색해진다. 일본어 기술 문서에서 실제로 쓰는 표현을 고른다
     (예: 「〜してみた」「〜という判断」「そもそも」).
   - 기술 고유명사는 원어 그대로. 무리해서 일본어로 바꾸지 않는다.
   - **의미를 보존한다.** 문장을 지우거나 없는 정보를 지어내지 않는다. 사실 관계와 판단의 근거는
     그대로, 표현만 일본어답게.

4. **파일 생성 후 검증.**

   ```bash
   npm run build
   ```

   분류 값을 잘못 복사했으면 여기서 빌드가 실패한다.

5. **보고.** 만든 경로와, 번역에서 판단이 필요했던 지점을 **한국어로** 짚는다
   (어느 표현을 왜 그렇게 골랐는지). 이 블로그는 일본어 작문 학습을 겸하므로 이 해설이 본론이다.
   다음 단계로 `/proofread-post <slug>`를 안내한다.

## 실패 대응

- **`ja/<slug>.md`가 이미 있음**: 덮어쓰기 전에 사용자에게 확인한다. 재번역인지, 원본이 바뀌어
  갱신하는 것인지 물어본다 (후자면 `npm run i18n:status`가 뒤처짐으로 잡아준 경우다).
- **원본이 `draft: true`**: 번역해도 되지만, 본문이 아직 바뀔 수 있으니 사용자에게 알린다.
