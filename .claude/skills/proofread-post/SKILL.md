# proofread-post

번역본을 다듬는 스킬. 핵심은 **git staging을 첨삭 장치로 쓰는 것**이다.
번역본을 index에 고정한 뒤 working tree만 교정하면 `git diff`가 그대로 "제안한 첨삭"이 되고,
사용자는 `-`(원문)/`+`(교정)을 나란히 보며 공부한다.

> 이 블로그에서 일본어를 쓰는 목적의 절반은 작문 학습이다. 그래서 교정은 조용히 고치는 작업이
> 아니라 **왜 그렇게 고쳤는지 해설하는 작업**이다.

## 절차

1. **대상 확인.** `src/content/blog/ja/<slug>.md`를 Read. slug를 못 받았으면 최근에 번역한
   파일을 확인한다. 일본어 파일이 아니면 되묻는다 (`ko/`를 교정하는 스킬이 아니다).

2. **원본을 stage에 고정.** 교정 편집보다 **반드시 먼저** 실행한다:

   ```bash
   git add src/content/blog/ja/<slug>.md
   ```

   이 stage된 버전이 diff의 비교 기준이 된다.

3. **본문만 교정.** frontmatter, 코드블록 내용, 링크 URL, 이미지 경로는 **그대로 둔다.**

   - **문법·조사·활용·오타**를 바로잡는다.
   - **원어민이라면 그렇게 쓰지 않을 표현**을 고친다. 문법적으로 틀리지 않아도 어색한 어순,
     뚝뚝 끊기는 연결, 한국어 직역투는 손본다. 문장을 합치거나 나누기, 접속 표현
     추가(`それで`, `〜のに`, `とはいえ`), 더 자연스러운 어휘로 교체 — 흐름이 매끄러워지는
     수정을 환영한다.
   - **기술 문서의 톤을 지킨다.** 일기가 아니므로 이모지를 넣지 않고, 과한 캐주얼체로 바꾸지
     않는다. 문체(だ・である체 / です・ます체)는 원문의 선택을 유지한다.
   - 기술 고유명사와 코드 식별자는 손대지 않는다.
   - **의미는 보존한다.** 문장을 지우거나 새 정보를 지어내지 않는다. 애매하면 원문 뉘앙스를 살린다.

4. **diff 제시 + 해설.**

   ```bash
   git diff src/content/blog/ja/<slug>.md
   ```

   주요 수정 항목을 **문장별로 diff + 코멘트를 묶어** 한국어로 해설한다.
   문법 근거를 포함하고, 어휘를 바꾼 경우 **왜 그 표현을 골랐는지** 설명한다
   (예: 한국어의 "확인하다"를 문맥에 따라 「確認する」가 아니라 「調べる」/「検証する」로 나누는 이유).

5. **다음 단계 안내.** 교정을 받아들일지는 사용자의 자유다. 확정한 뒤
   `npm run build`로 검증하고 commit·push하면 배포된다는 것을 알린다.
   `ko/` 원본을 나중에 고치면 `npm run i18n:status`가 뒤처짐을 잡아준다.

## 실패 대응

- **이미 다른 변경이 stage됨**: 이 파일만 재-add해도 diff 비교엔 문제없지만, 다른 stage된 변경이
  섞여 있으면 사용자에게 알린다.
- **파일이 아직 커밋된 적 없음**: `git add`만으로도 diff 기준이 생기므로 그대로 진행한다.
