サイドプロジェクトをつくっていると、「これはもう少し調べないとな」と思いながら通り過ぎる概念が次々に出てくる。このブログは、それを実際に調べ直して書き残す場所だ。だから記事が日付順に積まれるだけでは足りない。**どのプロジェクトから出てきて、どの分野に属するのか**で辿れるようにしたい。

## 三つの軸

| 軸 | 個数 | 性格 |
| --- | --- | --- |
| プロジェクト | 0〜1 | どのプロジェクトから出てきた問いか |
| 分野 | ちょうど 1 | 記事がどこに属するか |
| スタック | 0〜6 | 何についての記事か |

分野は `frontend` `backend` `mobile` `ml` `infra` `tooling` の六つに固定し、**必ず一つだけ**つける。複数を許すと結局すべてつけてしまい、軸が何の情報も与えなくなる。新しい分野が必要になったらコードに値を追加することになるが、その明示的な手間こそが分類の規律になる。

逆にスタックは自由な文字列だ。使う技術の名前は増えていくのが当たり前だからだ。

`auth` のようにフロントとバックエンドにまたがる話題は、分野ではなくスタックに置く。分野にしてしまうと軸同士が重なってしまう。

## 軸の値は言語に依存しないコードで

このブログは韓国語で書いて日本語に訳している。だから分類の値を表示名のまま保存すると、同じ分類が「バックエンド」と「백엔드」に割れてしまい、インデックスが半分ずつに分かれてしまう。

そこで保存するのは `domain: backend` の一つだけにして、表示名は言語ごとの辞書で与える。軸は一つに保たれ、表示名は後からいくらでも変えられる。

プロジェクトの id も同じ理由で、**リポジトリ名から取らない。** id は URL に埋め込まれるので、リポジトリ名が変わるとリンクが壊れる。プロジェクトそのものの中身から取った id にしておけば、リポジトリ名がどう変わっても URL は動かない。

## 間違った分類はデプロイされない

分野は enum で、プロジェクトは実在するプロジェクトファイルを参照する。だからタイプミスをしたり存在しないプロジェクトを指したりすると、**ビルドが失敗する。** 分類の壊れた記事がサイトに上がること自体が防がれる。

半年後に `infra` と `Infrastructure` が共存しているのを見つけるより、いまビルドが一度壊れるほうがいい。
